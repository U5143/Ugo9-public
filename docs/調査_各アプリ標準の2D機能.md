# エンジン標準機能だけで Live2D 風 2D キャラをどこまで再現できるか

調査日：2026-10-29（作業は UTC で 10-30 未明まで続いた。確認日はすべて 2026-10-29 と書く）

**問い**：2D キャラ制作ツールがモデルを各エンジンの「標準のオブジェクト」に変換し、変形と描画をエンジン側に任せる場合（ツール独自のランタイムやプラグインを使わない場合）、何ができて何ができないか。

**記号**
- ○＝標準機能でできる。△＝一部だけ、または工夫や自作シェーダーが要る。×＝標準機能ではできない
- （確認済み 2026-10-29）＝公式ドキュメントやソースコードを自分で開いて確かめた
- （二次情報）＝検索結果の抜粋、フォーラム、記事による
- （推測）＝自分の推論

## 2. 対象ごとの詳細

### 2.1 Unity（2D Animation／Sprite Skin、PSD Importer、Sprite Mask、URP 2D）

**スキニング**
- Sprite のボーン重みは `BoneWeight` 型のデータとして持つ（`SpriteDataAccessExtensions` は「VertexAttribute, BoneWeight, BindPose and the SpriteBones」を読み書きする、と書かれている）。`BoneWeight` は「Describes 4 skinning bone weights」で1頂点に4本固定。つまり Sprite Skin も1頂点4本（確認済み 2026-10-29）
- SkinnedMeshRenderer なら `BoneWeight1` を使い、「up to 255 bone weights per vertex」まで持てる。品質設定 `QualitySettings.skinWeights` で One／Two／Four／Auto を選べ、レンダラーごとにも上書きできる（確認済み 2026-10-29）
- 変形を GPU で行う機能（GPU Deformation）は 2D Animation 10（Unity 2023.1）以降で、URP 専用。SRP Batcher をオンにし、Player 設定の GPU Skinning を「GPU (Batched)」か「GPU」にする。条件を満たさないと CPU 変形と動的バッチに落ちる。ただし Android と Web では自動で CPU に落ちないので、自分で CPU を選ぶ必要がある。GLES3（Android）と WebGL では使えず、Vulkan か WebGPU が必要（確認済み 2026-10-29、GPUDeformation.html）
- 重さの目安（公式の勧め）：低ポリゴンの物が多い場面は CPU 変形、高ポリゴンの物が少ない場面は GPU 変形。Bounds Mode を「Bone Based」にすると、カリング用の範囲計算が速くなる（確認済み 2026-10-29）
- CPU 変形は Job で計算している（CHANGELOG 17.0.0 に「deformation bone job」とある）（確認済み 2026-10-29）
- 2D IK は標準で付いている（Limb／CCD／FABRIK）（確認済み 2026-10-29、TOC と CHANGELOG）

**頂点モーフ**
- 2D Animation には頂点ごとのキー（Spine の deform や Live2D のキーフォームに当たる物）が無い。マニュアルの目次にもブレンドシェイプは出てこない。部品の差し替えは Sprite Swap（Sprite Library／Sprite Resolver）で行う（確認済み 2026-10-29、TOC）
- 代わりの方法：平面メッシュを SkinnedMeshRenderer にして、ブレンドシェイプ（Mesh.AddBlendShapeFrame、途中の形のフレームも持てる）を Animator で動かす。描画順は Renderer 共通の sortingLayer／sortingOrder と Sorting Group で付けられる（推測：URP の 2D Renderer で SMR を描くと、ライティングなどに細かい違いが出る可能性がある）

**マスク**
- Sprite Mask はステンシルを使う（2D Renderer で Depth/Stencil Buffer を有効にするよう指示がある）。SpriteRenderer の Mask Interaction は None／Visible Inside Mask／Visible Outside Mask の3つで、**反転マスクも標準でできる**。マスクの元は Sprite か「Supported Renderer」（Sprite Renderer／Sprite Shape／Tilemap）。範囲は Alpha Cutoff で決まる**二値**で、境界は硬い。Custom Range でマスクが効く sorting layer の範囲を決め、Sorting Group で他のマスクと干渉しないようにする（確認済み 2026-10-29）
- 大きな制約：「Sprite masks aren't compatible with the SRP Batcher」で動的バッチに落ちる。さらに「falls back to using CPU deformation」で、GPU 変形も使えなくなる（確認済み 2026-10-29）
- Sprite Mask が効くのは SpriteRenderer だけ（確認済み 2026-10-29）。SMR で同じことをするには自作のステンシルシェーダーが要る（推測）

**色と合成**
- SpriteRenderer.color は色を掛ける（tint）。合成モードのプロパティは無く、マテリアルで決める（確認済み 2026-10-29、Sprite Renderer の資料）
- URP の Sprite 用 Shader Graph には Blending Mode があり、Alpha／Premultiply／Additive／Multiply を選べる（二次情報：検索結果に出た 6.x の資料の抜粋）。Screen は ShaderLab の Blend 指定で自作する（推測）
- **スクリーン色を部品ごとに付ける方法**：Unity 6.3 以降の Renderer Shader User Value（RSUV）が使える。SpriteRenderer にも `SetShaderUserValue(SpriteRenderer, uint)` があり、32bit の値をシェーダーの `unity_RendererUserValue` で読める。SRP 専用で、「without breaking SRP batches」（バッチを切らない）。ただし保存されないので、読み込み直すと 0 に戻る（確認済み 2026-10-29）。乗算は color、スクリーンは RSUV の 24bit、という分け方ができる（推測）
- MaterialPropertyBlock を使うと SRP Batcher が外れる（GPU 変形の条件にも「Avoid Material Property Blocks」とある）（確認済み 2026-10-29）

**パラメータ駆動**
- Animator のブレンドツリーには 1D／2D／Direct がある。Direct はパラメータ1つが子のモーション1つの重みに直接つながり、表情のブレンドシェイプを混ぜる用途が例に挙がっている（確認済み 2026-10-29）
- Live2D の格子状のキーフォーム（2つのパラメータの双線形補間）と同じ結果にするには、1D のブレンドツリーを入れ子にするか、Direct で重みをスクリプトから計算する（推測）

**読み込み**
- PSD Importer は .psb を読み、スプライトのプレハブを作る（Character Rig、Mosaic）。.psd もインポーターを切り替えれば読める。ただし **Blend Modes、Layer Opacity、Channels、Effects は無視される**（確認済み 2026-10-29、PSD Importer 16.0.1）
- glTF は glTFast（`com.unity.cloud.gltfast`、最新 6.20）（確認済み 2026-10-29：版だけ。スキンとモーフに対応しているかはページで確かめていない）

### 2.2 Godot 4.7（Skeleton2D／Bone2D／Polygon2D／CanvasItem）

**スキニング**
- Polygon2D に `skeleton`（Skeleton2D への NodePath）を指定し、重みはボーンごとに `add_bone(path, weights)`／`set_bone_weights` で渡す（確認済み 2026-10-29、クラス資料）
- ソース（`scene/2d/polygon_2d.cpp`）を読むと、頂点ごとに**重い順に4本だけ残し**、合計1に正規化してから `ARRAY_BONES`／`ARRAY_WEIGHTS` に詰めている（確認済み 2026-10-29、master）
- 変形は GPU で行う。RD レンダラー（Forward+／Mobile）ではコンピュートシェーダー（`mesh_storage.cpp` の `update_mesh_instances` が `SHADER_MODE_2D` でディスパッチ）。Compatibility（GLES3）ではトランスフォームフィードバック（`glBeginTransformFeedback`）（確認済み 2026-10-29、ソース）
- バッチ：RD の canvas レンダラーには「Mesh's can't be batched, so always create a new batch」とある。Polygon2D は内部でメッシュを作って `canvas_item_add_mesh` で描くので、**1部品につき描画1回**（確認済み 2026-10-29、ソース）

**頂点モーフ**
- Polygon2D の `polygon`（PackedVector2Array）は AnimationPlayer でキーを打てる。`Animation::interpolate_variant`／`blend_variant` は配列を要素ごとに補間・加算する。ソースには「artists like to use it for polygon animation」というコメントまである（確認済み 2026-10-29、`scene/resources/animation.cpp`）。つまり **AnimationTree でキーフォームをブレンドできる**
- ただし重い：polygon が変わるたびに、CPU で三角形分割（`Geometry2D::triangulate_polygon`）とメッシュの作り直し（mesh_clear と mesh_add_surface）をする。skeleton を付けていると毎回 clear される（確認済み 2026-10-29、ソース）。配列は Variant の要素ごとに処理されるので、頂点が多いと重い（推測）
- MeshInstance2D（ArrayMesh）にもブレンドシェイプを持たせられるが、2D 側からブレンドシェイプの重みを動かす API が無い（推測：canvas のメッシュインスタンスはスケルトンを付けたときだけ作られる、とソースから読める）

**マスク**
- `clip_children`：CLIP_CHILDREN_ONLY／CLIP_CHILDREN_AND_DRAW。「Clipping nodes cannot be nested or placed within a CanvasGroup」（入れ子にもできず、CanvasGroup の中にも置けない）。**反転モードは無い**（確認済み 2026-10-29）
- 仕組み：CanvasGroup と同じ仕組みで、バックバッファにコピーしてからクリップ用マテリアルで描く（確認済み 2026-10-29、`renderer_canvas_render_rd.cpp`）。マスクのαで掛けるので、境界は柔らかくなる（推測）
- 制約：マスクは**クリップされる部品の親**でなければならない。Live2D のように、ツリーのどこにあっても任意の部品をマスクにできる、という作りとは合わない。マスク用に同じスケルトンを付けた複製を親として置く方法が考えられる（推測）

**色と合成**
- modulate は子にも効き、self_modulate はその部品だけに効く（確認済み 2026-10-29）。Live2D のパーツ不透明度（子の各部品に掛かる）と同じ動きになる（推測）
- CanvasItemMaterial の合成は MIX／ADD／SUB／MUL／PREMULT_ALPHA。**Screen は無い**（確認済み 2026-10-29）
- インスタンスごとの uniform は「available in both canvas_item (2D) and spatial (3D) shaders」。1シェーダー16個まで（確認済み 2026-10-29）。スクリーン色は、共有の canvas_item シェーダーにインスタンス uniform を足せば作れる（推測）
- CanvasGroup は子をまとめて1枚として描き（バックバッファを使う）、重なった部分が濃くならない。グループの不透明度や、Cubism 5.3 のオフスクリーン描画に当たる。余白（margin）が大きいほど重い（確認済み 2026-10-29）

**揺れもの・IK**
- SkeletonModification2D（Jiggle／CCDIK／FABRIK／TwoBoneIK／LookAt／PhysicalBones）は 4.7 にもあるが「experimental」扱い（確認済み 2026-10-29）。Jiggle には stiffness・mass・damping・gravity と、コライダーを使う設定がある（確認済み 2026-10-29）
- 3D 側のような 2D 用 SkeletonModifier や SpringBone は見つからなかった（二次情報：検索で見つからなかった、というだけ）

**パラメータ駆動**
- AnimationNodeBlendSpace2D は「crossfading between the three adjacent ones」で、三角形分割による補間（確認済み 2026-10-29）。Live2D の格子（双線形）とは中の値がずれる。AnimationNodeBlendTree の Blend2 を入れ子にすれば、正確な多重線形になる（推測）

**読み込み**：PSD は標準で読めない。glTF は 3D 向け。Spine は公式の spine-godot（自前でエンジンをビルドするか GDExtension）。4.3 系の CHANGELOG に Godot 4.7 への対応とGDExtension の修正が並んでいる（確認済み 2026-10-29）。Live2D は有志の GDExtension（二次情報）

### 2.3 Unreal Engine 5.8

- Paper2D は Sprite・Flipbook・TileMap だけで、ボーンや変形の機能は無い（確認済み 2026-10-29）
- 2D キャラを動かすなら、平面の Skeletal Mesh にモーフターゲットとマテリアルを組み合わせる形になる（推測）
- スキニング：既定は1頂点4本か8本（プラットフォームで変わる）。Unlimited Bone Influences でも「in practice ... capped to 12」。モバイルは「75 bones per Section」まで。GPU の頂点シェーダーか Skin Cache（コンピュート）で計算する。Deformer Graph（Beta）は GPU だけの変形パイプライン（確認済み 2026-10-29、Skeletal Mesh Rendering Paths）
- glTF（Interchange）で読むと4本に切り捨てられる、という報告がある（二次情報：フォーラム）
- モーフターゲット：SetMorphTarget、アニメーションカーブ、Pose Asset で動かす。GPU で計算する設定がある（二次情報）
- 合成：Opaque／Masked／Translucent／Additive／Modulate（乗算）／AlphaComposite／AlphaHoldout。**Screen は無い**（確認済み 2026-10-29）。スクリーン「色」なら、マテリアル内で色を計算すればよい（推測）
- マスク：Custom Depth-Stencil はポストプロセスのマテリアルで CustomStencil を読む方式。部品ごとにステンシルで判定する標準の手段は無い。代わりは Render Target か、静的なマスクテクスチャ（二次情報＋推測）
- 描画順：半透明はコンポーネント単位の Translucent Sort Priority（二次情報：Blueprint API の資料）。描画順を途中で変える部品は、別のコンポーネント（Leader Pose で同じ骨を使う）に分ける必要がある（推測）
- 揺れもの：AnimDynamics は「light-weight physics simulation」。チェーンとばねを扱い、衝突は計算しない。Control Rig Physics は 5.8 で Beta（確認済み 2026-10-29）
- パラメータ駆動：BlendSpace（既定は三角形分割、Use Grid で旧来の格子）、Pose Asset ＋ Pose Blender／Pose Driver（確認済み 2026-10-29）
- 読み込み：FBX／glTF／USD。PSD Importer は Experimental のプラグイン（二次情報：API 資料）。Live2D の Cubism SDK for UE はアルファからベータへ（二次情報）。Spine は spine-ue

### 2.4 Web：PixiJS v8.22

- Mesh／MeshSimple／MeshPlane／MeshRope／PerspectiveMesh は、頂点を CPU の配列で持ち、書き換える作り（`geometry.positions[0] = 50`）。ボーンもスキニングも無い（確認済み 2026-10-29）
- バッチ：`Mesh.batched` は、自作シェーダーが無く、深度やカリングを使っておらず、`batchMode:'auto'` で **100頂点以下**ならバッチに入る（確認済み 2026-10-29、`Mesh.ts`）
- マスク：`setMask({ mask, inverse: true })` で反転できる（確認済み 2026-10-29、ガイド）。ソースでは StencilMask（Container なら何でもマスクにでき、ステンシルで二値）と AlphaMask（Sprite のテクスチャのチャンネルを使う。Sprite 以外はテクスチャに描いてから使う。inverse 可）がある（確認済み 2026-10-29）。アルファマスクはフィルターとして動くので、Render Target とパスが増える（推測）。1つの物に付けられるマスクは1つ（確認済み 2026-10-29）
- 合成：`mapWebGLBlendModesToPixi.ts` に normal／add／multiply／screen などがあり、GPU の合成で行う（確認済み 2026-10-29）。HARD_LIGHT などの高度な合成は `pixi.js/advanced-blend-modes` のフィルター（確認済み 2026-10-29）
- tint と alpha は子に受け継がれる。zIndex は sortableChildren と組み合わせて使い、子が多いと並べ替えが重い（確認済み 2026-10-29）
- 揺れもの・パラメータブレンドは無い。結局「JS で小さな変形エンジンを書く」ことになり、実質的には自前のランタイムになる（推測）

### 2.5 Web：three.js r186

- `skinning_vertex.glsl.js` は boneMatX／Y／Z／W の4本を GPU で計算している（確認済み 2026-10-29）
- モーフ：`morphTargetInfluences[ MORPHTARGETS_COUNT ]` を使い、頂点のずれをテクスチャから読む方式（確認済み 2026-10-29）
- 合成：NoBlending／NormalBlending／AdditiveBlending／SubtractiveBlending／MultiplyBlending／CustomBlending（確認済み 2026-10-29、constants.js）。Screen は CustomBlending で src を One、dst を OneMinusSrcColor にすれば作れる（推測）
- ステンシル：Material に stencilWrite／stencilFunc／stencilRef／stencilFail などがある（確認済み 2026-10-29、Material.js）。テクスチャの形をマスクにするには alphaTest が要る。反転は NotEqualStencilFunc（推測）
- GLTFLoader でスキン・モーフ・アニメーションを読める（推測：一般によく知られた機能。今回はページを開いていない）。物理と BlendSpace は無い

### 2.6 OBS Studio 33

- ブラウザソースは CEF（Chromium Embedded Framework）。背景を透過できる。fps を指定できる（既定 30）。GPU の起動オプションも渡せる（確認済み 2026-10-29）。Web で描いたキャラ（Pixi／three）をそのまま載せる形になる
- OBS 自体にもソース単位の機能がある：合成モード（`OBS_BLEND_NORMAL／ADDITIVE／SUBTRACT／SCREEN／MULTIPLY／LIGHTEN／DARKEN`）、Image Mask/Blend フィルター（静止画ファイルをアルファマスクにする、または乗算・加算・減算で重ねる）（確認済み 2026-10-29、obs.h と locale）
- obs-websocket の `SetSceneItemTransform`／`SetSceneItemIndex`／`SetSceneItemBlendMode` で、外から部品の位置・順番・合成を動かせる（確認済み 2026-10-29、protocol.md）。PNGTuber のように「部品を切り替えて動かす」ことは OBS 標準でもできる。メッシュの変形はできない

### 2.7 VTuber アプリ

- **VTube Studio**：メインのモデルは Live2D だけ（Live2DModels フォルダ、ArtMesh 単位の API）。プラグインからは `ItemLoadRequest` の `customDataBase64` で PNG／JPG／GIF を読み込める。条件は 64〜2048px、5MB 未満、GIF は1024フレームまで。「Custom data Live2D items are not currently supported」（確認済み 2026-10-29）。パラメータは `InjectParameterDataRequest`、色は ArtMesh への tint で動かせる。**他の描画エンジンの映像を、連続した絵として流し込む API は無い**（確認済み 2026-10-29：README に該当する項目が無い）
- **Warudo**：読めるのは .vrm と .warudo。.warudo は Mod SDK（Unity 2021.3.45f2 を厳密に指定）で作る。Mod には C# のスクリプト（.cs）を入れられるが、asmdef・コンパイル済み DLL・ScriptableObject・UnityEditor を参照するコードは使えない（確認済み 2026-10-29）。2D Animation パッケージは asmdef と ScriptableObject（Sprite Library）を使うので、そのままは入らない（推測）。ブループリントの見本に「Live2D Arm Sway」「Live2D Eye Wiggle」がある（3D モデルを Live2D 風に揺らすもの）（確認済み 2026-10-29：サイドバーの項目名）
- **VSeeFace**：VRM か VSFAvatar（Unity 2019.4.31f1 の AssetBundle）。使えるコンポーネントのホワイトリストに `SpriteRenderer`、`SpriteMask`、`SkinnedMeshRenderer`、2D 物理（Rigidbody2D・HingeJoint2D・SpringJoint2D など）は**ある**が、2D Animation（U2D）の Sprite Skin は**無い**。URP のシェーダーは使えない（確認済み 2026-10-29、README）
- **使えそうな道**：平面メッシュの VRM にする。VRM 1.0 の表情は morphTargetBinds・materialColorBinds・textureTransformBinds を持ち、揺れものは VRMC_springBone で付けられる（確認済み 2026-10-29、vrm-specification）。ただし、顔の向き（AngleX／Y）を「モーフ」として動かすかどうかはアプリ次第。Warudo はブループリントで組める。VSeeFace は標準の表情とパーフェクトシンクの範囲だけ（推測）

## 4. 最も大きい穴 5つ

1. **ワープデフォーマ（格子・FFD）と、デフォーマの入れ子**。標準で持つエンジンは1つも無い。格子の点1つをボーン1本にすれば、双線形補間なら1頂点4本の重みで表せる。ちょうど4本の上限に収まる（推測：Cubism のワープが格子の4点による双線形と仮定した場合）。ただし入れ子のワープや、パラメータで格子自体が動く場合は線形にならないので、パラメータの組み合わせごとにモーフへ焼き込むか、近似するしかない。Live2D の「顔の角度 XY」の見た目の中心がここにある
2. **2D の頂点モーフ（キーフォーム）**。Unity の 2D Animation（Sprite Skin）には無い。Godot は polygon 配列で CPU による作り直し。Pixi には無い。モーフが GPU で動くのは Unity-SMR／UE／three だけ。さらに、2パラメータの格子補間（双線形の掛け算の項）は、BlendSpace2D／UE BlendSpace の三角形分割とは一致しない。1D を入れ子にするか、スクリプトで重みを計算する必要がある
3. **任意の部品を使うクリッピングと反転マスク**。Unity の Sprite Mask は反転できるが、二値で、SRP Batcher も GPU 変形も無効になる。Godot の clip_children は親子のときだけで、入れ子にも反転にもできず、バックバッファのコピーも要る。UE には部品ごとのステンシルが無い。素直にできるのは Pixi と three.js（ステンシルかアルファマスク、反転あり）だけ
4. **スクリーン色と、Cubism 5.3 の高度な合成モード（オフスクリーン描画）**。部品ごとのスクリーン色を標準で持つエンジンは無く、自作シェーダーが要る。Unity は RSUV ならバッチを切らずに済む。Godot はインスタンス uniform（16個まで）。Overlay や SoftLight などは部品のグループを Render Target に描く必要があり、Godot の CanvasGroup や Pixi のフィルターでは描画のたびにコピーやパスが増える
5. **グルーと揺れもの、VTuber アプリの入口**。グルーはどこにも無い。継ぎ目の頂点に同じ重みと同じモーフの変位を与えて、変換時に焼き込むしかない。2D の揺れもの物理は Godot（実験的な Jiggle）、UE（AnimDynamics）、VRM（SpringBone）だけで、Unity 2D と Web には無い。VTuber アプリは VTS が Live2D だけ（プラグインは静止画と GIF を足せるだけ）、VSeeFace と Warudo は 3D の VRM／Unity バンドルだけ。現実的な入口は「平面の VRM」

その次の穴：描画順の切り替えと部品の数による負荷。Godot はメッシュをバッチしないので1部品1回の描画。UE は描画順の単位がコンポーネント。Pixi は100頂点を超えるとバッチから外れる。

## 5. 変換ツールを作る場合の設計メモ（推測）

- 出力先ごとの「一番素直な標準の組み合わせ」
  - Unity：SkinnedMeshRenderer（平面）＋ブレンドシェイプ＋Animator（1D を入れ子、または Direct）＋SpriteRenderer.color か RSUV で色＋自作のステンシルシェーダー。Sprite Skin はモーフが要らない部品だけに使う
  - Godot：Polygon2D＋Skeleton2D（GPU スキン）。キーフォームは polygon 配列のキー＋AnimationTree の Blend2 の入れ子。CPU の負荷が大きいので、モーフは顔などに絞る。clip_children の制約に合わせてツリーを組み直す
  - UE：平面の Skeletal Mesh＋モーフ＋Pose Asset。描画順が変わる部品は別コンポーネント。マスクは Render Target（重い）
  - Web：three.js の SkinnedMesh＋morph＋stencil が「標準だけ」で一番広く届く。Pixi はスキンとモーフを自前で書く必要がある
  - VTuber：平面の VRM 1.0（表情＝モーフ、SpringBone、MToon）
- 変換するときに焼き込む物：ワープ（格子ボーンかモーフへ）、グルー（重みとモーフの変位を揃える）、親デフォーマの連鎖（ボーンの階層へ）、パーツ不透明度の継承（エンジンが継承しない場合は子の色へ掛け込む）
