## 全体の形

```

  └ タグ v0.1.0 を打つ → GitHub Actions（Windows）で tauri build
       ・インストーラー（NSIS の .exe）と、更新の署名（.sig）・latest.json を作る
```

## ソースをどこでビルドするか（3 つの案）

| 案 | 中身 | 公開側に見える物 | 使用量・手間 |
|---|---|---|---|
| **A（おすすめ）非公開側の CI でビルドし、公開側へリリースだけ上げる** | このリポジトリの Actions でタグの時だけ Windows でビルドし、細かい権限のトークンで配布用リポジトリのリリースに上げる（相談窓口が別の Tauri アプリで使っている形） | リリースの成果物（.exe・.sig・latest.json）と、リリースの説明文だけ。ビルドのログは非公開側に残る | 非公開の Windows は使用量が 2 倍に数えられる。1 回のビルドで 10〜15 分 × 2 ＝ 20〜30 分ほど。タグの時だけなので少ない |
| B 公開側の CI が、鍵で非公開のソースを読んでビルド | 配布用リポジトリの Actions が、読み取り専用の鍵でこのリポジトリを取り出す | **ログが公開になる**（ファイル名・ビルドの出力・失敗した時のソースの一部が見える）。鍵の扱いを誤るとソースが漏れる | 公開リポジトリの標準ランナーは無料 |
| C ユーザーの PC でビルドして手で上げる | `npm run build`（desktop/）で作り、配布用リポジトリのリリースに手で上げる | 成果物だけ | CI を使わない。毎回の手間と、署名の鍵を PC に置く必要がある。Rust と Visual Studio の C++ ビルドツールが要る |

A をすすめる理由：ソースとログを公開しないまま、使用量はタグの時だけで小さい。今月の利用枠が切れている間は、C で最初の版を出し、来月から A に切り替える手もある。

## ユーザーがすること

1. **配布用リポジトリを作る**（公開。**作る時に「Add a README file」に印を付ける**。空のリポジトリにはブランチが無く、`main` を指すリリースを作れない。README は後で配布用 README に置き換える）
   - 名前の案：**`U5143/ugo9-editor`**（おすすめ。何が手に入るか分かる）／`U5143/ugo9-releases`（配布だけと分かる）／`U5143/ugo9`（製品の顔にする。ソースの Ugo9 と紛らわしい）
2. **更新の署名の鍵を作る**（自分の PC で。鍵はこのセッションやチャットに貼らない）
   - `cd desktop && npx tauri signer generate -w ~/.tauri/ugo9-updater.key`（合言葉を決める）
   - 出てきた**公開鍵**（.key.pub の中身）はハブに渡してよい（公開して問題ない物）
3. **トークンを作る**：GitHub の Fine-grained personal access token。対象のリポジトリは `ugo9-editor` だけ、権限は Contents: Read and write
4. **秘密を置く**：このリポジトリ（U5143/Ugo9）の Settings → Secrets and variables → Actions に、下の表の物を置く
5. **最初の版を出す**：準備ができたらハブに伝える（こちらでタグを打つか、ユーザーが打つ）。リリースは下書きで作られるので、中身を確かめてから Publish する

### 置く秘密と変数（このリポジトリの Actions）

| 名前 | 種類 | 中身 |
|---|---|---|
| `TAURI_SIGNING_PRIVATE_KEY` | Secret | 更新の署名の秘密鍵（`ugo9-updater.key` の中身） |
| `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | Secret | 鍵を作った時の合言葉 |
| `RELEASE_TOKEN` | Secret | 配布用リポジトリへ上げるトークン（Contents: Read and write） |
| `UGO9_UPDATER_PUBKEY` | Variable | 更新の署名の公開鍵（秘密ではない） |
| `UGO9_RELEASE_REPO` | Variable | 配布用リポジトリ（例 `U5143/ugo9-editor`） |

公開鍵と配布先は、ビルドの時に CI だけが入れる。手元のビルドは更新を確かめない（相談窓口の答えの形）。

## 作りの細かい所

- 更新の公開鍵と見に行く先（`https://github.com/<配布用>/releases/latest/download/latest.json`）は、CI がビルドの時に環境変数（`UGO9_UPDATER_PUBKEY`・`UGO9_UPDATE_ENDPOINT`）で渡し、Rust の `option_env!` で埋め込む。無いビルド（手元・開発）は更新を確かめない
- 更新の署名の成果物（`createUpdaterArtifacts`）と公開鍵は、CI の時だけ `desktop/scripts/release-config.mjs` が作る `tauri.release.conf.json` で足す（設定ファイルに空の鍵を置いたまま署名すると止まる、という相談窓口の答え（別の Tauri アプリでの経験）から）
- `tauri.conf.json` の `plugins.updater` は空の値を置いておく（無いと起動時に止まる）
- CI は `vars.UGO9_RELEASE_REPO` が無いと動かない（準備ができるまで何もしない）
- 秘密を渡す外部のアクション（checkout・setup-node・rust-toolchain・rust-cache・tauri-action）は、タグではなくコミットの SHA に固定している（タグは後から動かせるため）。上げる時は、新しい版の SHA を確かめて書き換え、コメントの版名も直す
- 配布用リポジトリは、作る時に README を付けて main ブランチを作っておく（`releaseCommitish: main` のリリースは、ブランチの無い空のリポジトリには作れない）
- リリースは下書き。中身を確かめてから Publish すると、アプリの更新に届く
- 保存の置き換え：Windows は `MoveFileExW`（`MOVEFILE_REPLACE_EXISTING | MOVEFILE_COPY_ALLOWED | MOVEFILE_WRITE_THROUGH`、`windows-sys`）。前の「rename が断られたらコピーで上書き」は、途中で失敗すると前のファイルも壊れるのでやめた
- WebView2 のページのプロセスが落ちたら（`ProcessFailed`）、ページを読み込み直す（1 分に 2 回まで）。読み込み直すと、保存していない作業の控えから「戻す」が出る
- アプリの識別子 `app.ugo9.editor`（`tauri.conf.json` の `identifier`）は**変えない**。WebView2 の保存領域（localStorage：最近開いたファイル・言語・自動キー・XY のくっつき・保存していない作業の控えなど）は識別子ごとに分かれるので、変えると、入れ直した人の設定と控えが全部消えたように見える
- `desktop/dist` を作り直す時は、`fs.rmSync` を使わず、自分で中を消す（`copy-dist.mjs` の `removeTree`）。Node 24 の `fs.rmSync({ recursive })` が、日本語の名前を含むパスで何も言わずにプロセスごと落ちた例がある（別のアプリ、Windows、0xC0000409）
- 画面の HTML と JS では、`style` 属性を使わない（JS は `el.style`、HTML はクラス）。Tauri が CSP にハッシュや nonce を足すと `'unsafe-inline'` が無視され、`style` 属性が効かなくなる。editor_test が厳しい CSP の下で確かめている

### できた後

- ユーザーが下書きを確かめて Publish する。以後の版は、Actions の枠が戻ったら CI（タグ v*）で作る
- 公開鍵は `UGO9_UPDATER_PUBKEY`（Variable）に、秘密鍵と合言葉は Secrets に置く（「置く秘密と変数」の表）。PC で作った鍵と同じ物を使わないと、最初の版から後の版へ更新できない

### 入れた版で「はじめての 1 体」を試す（ユーザーが手で）

入れたデスクトップ版で、手持ちの PSD から 1 体を作ってみる。手順は docs/エディタの使い方.md の「はじめての 1 体（近道・7 手）」と同じ。時間があれば「1 つずつ作る（15 手）」も試す。

1. 試す PSD を選ぶ
   - 顔（輪郭）・目（左右で別のレイヤー）・口・体が、別のレイヤーになっている物
   - 名前に「目」「eye」「口」「mouth」、左右に「L」「R」「左」「右」が入っていると、自動の所がうまく働く
   - 他の人が描いた絵を使う時は、使ってよい物かを確かめる（スクリーンショットをハブに渡す時も同じ）
2. 近道の 7 手を順に進める。各手で「見える物」の列のとおりになるかを見る
3. 最後に GIF と .ugo を書き出し、「保存」で JSON とアトラスを残す
4. 保存した JSON を、アプリを閉じて開き直しても同じに見えるかを見る
5. 右上の「このアプリについて」で、利用規約と部品の一覧が出るかを見る
6. 何か変えて保存しないまま窓を閉じようとし、閉じてよいか聞かれるかを見る。「いいえ」で閉じずに残り、「はい」で閉じる。もう一度開くと「保存していない作業の控えがあります」と出て、「戻す」で戻るかを見る

### うまく行かない時に、ハブへ持ち帰る物

次をそろえて、ハブのセッションに貼るか添えてもらえると、エディタのセッションで直せる。

| 持ち帰る物 | 取り方 |
|---|---|
| どの手で、何をしたら、何が起きたか（起きなかったか） | 「8 で『顔の向きを自動で作る』を押したら、目が付いてこなかった」のように、手の番号と押したボタンの名前で |
| 画面の写し | Windows の Win＋Shift＋S。おかしい所と、下の状態の行（知らせの文）が入るように |
| 状態の行の文と「注意 n 件」の中身 | 下の行の文をそのまま書き写す。「注意 n 件」を押すと一覧が出るので、それも写す |
| PSD の作り | レイヤーとフォルダの名前の一覧（描くアプリのレイヤーの欄の写しで良い）、大きさ（幅×高さ）、色の深さ（8・16 ビット）。PSD そのものは、渡してよい物の時だけ |
| 保存した JSON | 開き直すとおかしい時は、保存した .json（とアトラスの画像）。渡してよい物の時だけ |
| 版 | 「このアプリについて」の上に出る版の番号 |
| 止まった・固まった時 | アプリを閉じて開き直して、同じ手で同じことが起きるか |

- PSD・JSON・画像は、他の人が描いた物なら渡さない。代わりにレイヤー名の一覧と画面の写しだけで良い
- 秘密鍵・合言葉・トークンは、どの写しにも入らないように気を付ける
