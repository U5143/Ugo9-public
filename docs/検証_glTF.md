# 検証：glTF は VTuber・ゲーム用の書き出しに適しているか

2026-10-29。Ugo9 の見本のキャラを glTF 2.0 に書き出し、公式の検証器・three.js（Web）・Godot（ゲームエンジン）で実際に読み込み、Ugo9 の描画と比べた。Unity・Unreal はこの環境で動かせないため、公式文書で確かめた（下の「エンジンごとの対応」）。

## 結論

**glTF は「形の入れ物」と「焼いたアニメの再生」には十分に使えるが、VTuber・ゲーム用の主な書き出し先には向かない。**

- 形・骨・差分（ブレンドシェイプ）・描く順番は、three.js でも Godot でも Ugo9 と同じに再現できた（値の誤差は 10⁻⁷、絵の差は輪郭の数ピクセルだけ）
- しかし glTF には「パラメータ → 差分の重み」の仕組み（範囲・角の補正・揺れ物の物理）が入らない。トラッキングやゲームの状態で動かすには、結局どのエンジンでも Ugo9 と同じ計算をするコードが要る
- 不透明度のフェード（まばたきの切り替えなど）は、どのエンジンでも使える形では書けない（表示／非表示の切り替えだけになる）
- 大勢を出すと重い：200 体で CPU の時間が Ugo9 の約 15 倍、描画命令が 200 回（Ugo9 は 1 回）。スマホ相当に CPU を遅くすると、100 体前後で CPU だけで 60fps の枠を使い切る（Ugo9 は 400 体で枠の 2 割以下）
- ブレンドシェイプの数が増えると、three.js・Babylon は全数に比例して重くなる（Ugo9 は頂点ごとに関係する差分だけを読む）

そこで、書き出しは次のように分けるのがよい（推測）。

| 用途 | 主な書き出し | glTF の使いどころ |
|---|---|---|
| 動画（GIF・APNG・MP4・WebM・連番） | 絵に焼く（`ugo_export`、ブラウザの書き出し） | 使わない |
| VTuber（トラッキングで動かす） | `.ug9`＋Ugo9 ランタイム（Web、各エンジンのプラグイン） | 使わない（下の VRM も 2D の振り向きには合わない） |
| ゲーム（状態で動かす・大勢を出す） | `.ug9`＋Ugo9 ランタイム | **補助**：Ugo9 のプラグインが無い環境、3D の場面に置く時、Blender などの道具へ渡す時に、焼いたアニメ付きで渡す |

## 試したこと

`tools/export_gltf.mjs` が `.ug9` から `.glb` を作る。

- 1 枚のメッシュ（パーツは描く順に三角形を並べる）、1 つの素材（光を受けない・半透明・両面）
- 骨は glTF のノード（y を上向きに直し、1 px = 1 cm）
- Ugo9 の差分を、そのままブレンドシェイプにする（変わる頂点だけを持つ sparse 形式）
- 不透明度が変わるパーツ（目・閉じた目）は、専用の「表示用の骨」を付け、隠す時はその骨を 0.0001 倍に縮める
- アニメーションは Ugo9 のランタイムで 30 fps ごとに計算して焼く（骨の動き＋全ブレンドシェイプの重み）

試行錯誤で分かったこと：

- **隠すのにブレンドシェイプ（頂点を1点に集める）を使うと、細い線が残る。** 他の差分（振り向き・目を閉じる）が足されて点がずれるため。骨を縮める方式に変えて解決した
- **アニメごとに動かす物が違うと、切り替えた時に前のアニメの姿が残る**（Godot で確認）。どのアニメにも「どれかのアニメで動く物」を全部キーとして書くようにした。さらに Godot は読み込み時の初期設定「Remove Immutable Tracks」で、値が変わらないキーを消してしまうため、この設定を切る必要がある

## 結果

### 規格に合っているか

Khronos の公式検証器（gltf-validator 2.0.0-dev.3.10）：**エラー 0・警告 0**。描画命令 1、頂点 2,034、三角形 3,362、ブレンドシェイプ 13。

### 同じ絵になるか

| 比べた物 | 結果 |
|---|---|
| three.js r186 で焼いたアニメを再生（6 コマ）と Ugo9 | 形・順番は同じ。差は輪郭のふち取りだけ（平均 0.1〜0.26/255、差が 16 を超える画素は 0.1〜0.4%） |
| まばたきの途中のコマ | Ugo9 はフェード、glTF はパッと切り替わる（差が出る唯一の場所） |
| three.js を Ugo9 のランタイムで直接動かす（焼かずに、パラメータを変えて） | 同じ形。違いは半分閉じた目の透け方だけ |
| Godot 4.7.2 で読み込み | 骨 15・ブレンドシェイプ 13・メッシュ 1・アニメ 2（それぞれ 29 トラック）。ある時刻の値が Ugo9 と一致（ブレンドシェイプ・骨の位置・角度の誤差 10⁻⁷ 以下）。表示用の骨も正しく切り替わる |
| Godot で描画（Compatibility、ソフトウェアの OpenGL） | 正しく描けた。Godot は半透明を「先に深度を書く」方式で読み込むが、平らなキャラでも順番は崩れなかった。Ugo9 の参照画像との差は輪郭のみ（差が 16 を超える画素 0.8%、Godot 側にアンチエイリアス無し） |

### 重さ（大勢を出した時）

headless Chromium（ソフトウェアの GPU）、1 フレームあたりの CPU の時間。

| 体数 | three.js で glTF を再生 | 同（両面の2回描きを止めた時） | Ugo9 |

## エンジンごとの対応（公式文書・ソースで確認）

詳しい表と出典（ページ単位の URL）は [検証_glTF_エンジンの対応.md](検証_glTF_エンジンの対応.md)。2026-10-29 時点の最新版で確かめた。Unreal だけは Epic の文書の本文が取れず、根拠が弱い（API の一覧・掲示板・描画方式のページによる）。

| | Unity glTFast 6.20 | Unreal 5.8（Interchange） | Godot 4.7.2 | three.js r186 | Babylon.js 9.33 |
|---|---|---|---|---|---|
| 1頂点の骨の数 | 4 | 4（5 本目以降は捨てる） | 8 | 4 | 8 |
| ブレンドシェイプの重さが比例するもの | 動いている数 | 動いている数 | 全数のループ（読むのは動いている物） | 全数のループ（読むのは動いている物） | **全数**（9.14 からの既定） |
| 不透明度のアニメ（KHR_animation_pointer） | × | × | ○ | 本体は ×（外部のプラグインで ○） | ○ |
| 光を受けない材質（KHR_materials_unlit） | ○ | ○ | ○ | ○ | ○ |
| 半透明の深度 | 書かない | 書かない（推測） | **先に深度を書く方式**で読み込む | 書かない | 書かない |
| 同じ深さの物どうしの順番 | 決まらない（推測） | 境界球までの距離 | 安定しない | 作った順（安定） | 3D の距離 |

ここから言えること：

1. **描く順番がどのエンジンでも守れる形は1つだけ。** キャラ全体を1つのメッシュ・1つの素材・1枚のアトラスにし、三角形を奥から手前の順に並べ、深度を書かない形（今回の書き出しはこの形）。パーツや素材を分けると、エンジンごとに物体単位の距離で並べ替えられ、同じ深さの時の順番がばらばらになる
2. **パーツの不透明度を、どこでも動く形で書く方法は無い。** 素材の透明度を動かす拡張は Godot・Babylon などでしか動かず、しかも素材を分ける必要があるので 1. と両立しない。頂点色の透明度をブレンドシェイプで動かす方法は three.js と Babylon しか読めない（Unity・Godot・Unreal のブレンドシェイプは位置・法線・接線だけ）
3. **ブレンドシェイプが 100 個になると、エンジンによっては全数に比例して重くなる**（three.js・Babylon）。three.js は全部を密なテクスチャに持つので、2.5 万頂点 × 100 個で位置だけでも約 38 MB の見積もり。Ugo9 は頂点ごとに自分に関係する差分だけを読む
4. **Unity の SkinnedMeshRenderer は GPU インスタンシングができず、Unreal はスマホで 1 区画 75 本の骨まで**（超えると分割されて描画命令が増える）
5. **VRM 1.0（VTuber 用の glTF）でも、頭の向きでブレンドシェイプを動かす決まりは無い。** 頭の左右・上下は人型の骨（head）の回転で表すので、平らな 2D のキャラは板が回るだけになる。視線を表情に流せるのは目だけ。VTube Studio は Live2D 専用、VSeeFace は VRM 0 だけ。平らな 2D モデルを VRM として役立てているアプリは見つからなかった

## スマホでの軽さ

### この環境で測れたこと（スマホを真似た Chromium）

画面を 360×640、端末を Pixel 7 として、Chrome の機能で CPU を 4 倍遅くした（Lighthouse がスマホの中位機を真似る時と同じ倍率）。ここの GPU はソフトウェアで真似ているだけなので **fps はスマホの値ではない**。比べられるのは、1 コマを作るのに JavaScript が使った **CPU の時間**だけ（`tests/bench_emulate.mjs`）。

| 体数 | Ugo9 | CPU で変形（Live2D・Spine 型） | glTF（three.js） |
|---|---|---|---|
| 50 | 1.3 ms | 8.4 ms | 7.4 ms |
| 100 | 1.9 ms | 16.1 ms | 12.4 ms |
| 200 | 2.0 ms | 53.3 ms | 38.2 ms |
| 400 | 2.8 ms | 61.8 ms | 77.0 ms |

60fps の 1 コマは 16.7 ms（GPU の時間も含めて）。CPU を 4 倍遅くした条件では、CPU で変形する方式と glTF は 100 体前後で CPU だけでこの枠を使い切る。Ugo9 は 400 体でも 2.8 ms（枠の 2 割以下）。

### スマホの GPU について（推測）

- Ugo9 は頂点の変形を GPU に移すので、スマホでは GPU の頂点処理が増える。1 頂点あたりの仕事は「自分に関係する差分の数＋骨 4 本」で、見本では差分が平均 3 個ほど。描画命令が 1 回なので、タイル方式のスマホの GPU と相性がよい
- 使う機能（頂点シェーダーでのテクスチャ読み込み、RGBA32F のテクスチャ、整数の頂点属性）は WebGL2（OpenGL ES 3.0）の必須機能で、WebGL2 が動くスマホなら動く
- どの方式でも、重なった半透明を塗る量（フィルレート）は同じ。キャラを大きく表示するとそこが壁になる

### 実機で測る

端末で開くだけで測れるページ（`tools/make_bench_page.mjs` で作る）で測った。数字は 1 コマあたりの fps と CPU の時間。

**Pixel 9**（GPU Mali-G715、8 コア、Claude アプリの中のブラウザ、画面 60 Hz で測定、2026-10-29）

| 体数 | Ugo9 | CPU で変形（Live2D・Spine 型） | glTF（three.js） |
|---|---|---|---|
| 1 | 60 fps・0.36 ms | 60 fps・0.76 ms | 60 fps・1.50 ms |
| 10 | 60 fps・0.57 ms | 60 fps・4.95 ms | 60 fps・2.92 ms |
| 50 | 60 fps・1.19 ms | 60 fps・5.15 ms | 60 fps・2.74 ms |
| 100 | 60 fps・1.55 ms | 60 fps・6.09 ms | 60 fps・5.19 ms |
| 200 | 60 fps・3.71 ms | 60 fps・9.33 ms | 60 fps・7.64 ms |
| 400 | 60 fps・5.55 ms | 60 fps・12.04 ms | 60 fps・10.17 ms |

- 3 方式とも 400 体まで 60 fps を保ち、限界には届かなかった。上位のスマホでは、この見本の大きさのキャラなら、どの方式でも 400 体までは滑らか
- 差は CPU の時間に出た。400 体で Ugo9 は 5.6 ms、CPU で変形は 12.0 ms、glTF は 10.2 ms。Ugo9 は他の方式の半分以下で、電池の減りと発熱に効く。CPU で変形する方式は 60 fps の枠（16.7 ms）の 7 割を CPU だけで使っており、ゲームの処理を足す余裕が少ない
- 限界を知るため、ページを「滑らかでなくなるまで 2 倍ずつ（最大 3,200 体）」に変えた。中位・下位のスマホでも測ると、差がはっきりする見込み（推測）

## 再現の手順

```
npm install --no-save three@0.186.1 gltf-validator@2.0.0-dev.3.10
node tools/export_gltf.mjs samples/basic/model.ug9 build/gltf/basic.glb
node tests/gltf/validate.mjs build/gltf/basic.glb   # 公式の検証器
node tests/gltf_test.mjs                # three.js との比較と計測 → build/gltf/results.json
node tests/gltf/expected.mjs            # Godot と比べる値 → build/gltf/expected.json
# Godot（4.7.2）：空のプロジェクトのフォルダを用意して
godot --headless --path <空のプロジェクト> --script tests/gltf/verify_godot.gd -- build/gltf/basic.glb build/gltf/expected.json keep
xvfb-run godot --rendering-driver opengl3 --resolution 420x600 --path <空のプロジェクト> --script tests/gltf/render_godot.gd -- build/gltf/basic.glb build/gltf
```
