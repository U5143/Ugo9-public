# 設計

## 何を解決するか

Live2D・Spine は、ポリゴン（頂点）を増やすと重くなります。調べると、原因は頂点の数そのものではなく、次の作りでした（2026-10-29 の調査、情報収集リポジトリの `knowledge/2Dアニメ技術/`）。

- **全部の頂点を CPU で毎フレーム計算し直し、毎フレーム GPU へ送り直している**
- Live2D：パーツ（アートメッシュ）1枚ごとに描画命令を出し、マスクは別の画面に描いてから使う
- Spine：「頂点の数 × その頂点を動かす骨の数」の計算と、CPU で三角形を切るクリッピング

Ugo9 は、この作りを変えます。

| | Live2D・Spine | Ugo9 |
|---|---|---|
| 頂点の変形 | CPU が毎フレーム全部 | GPU のシェーダーが並列で |
| 毎フレーム GPU へ送る物 | 全頂点の位置（頂点数に比例） | 1体あたり数百バイトの「重み」（骨の行列・差分の重み・不透明度） |
| 描画命令 | パーツごと・キャラごと | 何体いても 1 回（インスタンス描画） |
| 表情・角度の持ち方 | パラメータの組み合わせごとに形（掛け算で増える） | パラメータごとの差分を足し算（可変フォントと同じ） |

## 「ランタイム」について

「ランタイム」は、ゲームや Web ページの中でデータを再生する小さなプログラムのことです。Live2D・Spine にも必ずあり、重さの元はその中で**毎フレーム何をするか**です。

Ugo9 のランタイムが毎フレーム CPU でするのは、パラメータの値から数百バイトの重みを作ることだけで、200 体でも 0.1 ms ほどです（下の計測）。重い頂点の計算は GPU が行います。GPU は数千の頂点を同時に処理する装置なので、頂点を増やしても見た目の重さはほとんど変わりません。

さらに、操作に反応しなくてよい場面（待機ループ・演出・SNS 用の GIF・動画）では、**前もって絵や動画に焼いて**しまえば、再生時の計算はゼロです（`ugo_export`、ブラウザの書き出し）。

用途で使い分けます。

| 用途 | 方式 | 再生時の計算 |
|---|---|---|
| ゲーム・配信（操作やトラッキングに反応） | パラメータ再生（CPU で重み → GPU で変形） | CPU は数百バイト、GPU は頂点ごと |
| GIF・APNG・動画・スプライトシート | 焼いた絵 | なし（画像・動画として再生） |
| 群衆・待機ループ（予定） | 焼いた頂点（頂点位置をテクスチャに） | GPU がテクスチャを読むだけ |

## 全体の流れ

```
作業用 JSON（人・エディタ・スクリプトが書く）
   │  tools/compile.mjs  … 検証・骨の並べ替え・差分を頂点ごとの疎な表に・名前の表
   ▼
配布用 .ug9（バイナリ、読み込み時にそのまま使える）
   │  ugo_model_init  … 全部の番号と範囲を検査（壊れた・悪意のあるファイルでも落ちない）
   ▼
毎フレーム（CPU、芯）
   パラメータ ← アニメーション（重ねがけ可）← 手入力・トラッキング
   → 揺れ物の物理（パラメータのばね）
   → 範囲（テント）ごとの重み → 差分の重み・骨の行列・不透明度 ＝ 「フレームの塊」（数百バイト）
   ▼
GPU（頂点シェーダー）
   基準の位置 ＋ Σ 重み × 差分 → 骨で動かす（最大4本） → キャラの位置 → 画面
```

同じ計算を CPU でもできます（`ugo_deform_cpu`、`ugo_raster_instance`）。書き出し・テスト・GPU が無い環境で使い、GPU の結果と同じになることをテストで確かめています。

## 足し算のキーフォーム

OpenType の可変フォントは、文字の太さ・幅などの軸ごとに「基準の形からの差分」を持ち、今の値に応じた重みを掛けて足します。必要な所だけ「2つの軸の角の補正」を足します。Live2D のキーフォームは軸の組み合わせごとに形を持つので、軸を増やすと数が掛け算で増えます。

Ugo9 の「範囲（region）」は可変フォントと同じ形です。

- 軸ごとに `[start, peak, end]` のテント：peak で 1、start・end で 0、その間は直線
- 複数の軸を持つ範囲は、各軸のテントの積（角の補正に使う）
- 差分・骨の動き・不透明度は「範囲の重み × 量」を足す

見本では、振り向き（AngleX／AngleY）・目の開閉・口・視線の差分を別々に持ち、全部の組み合わせが足し算で出ます。

## フレームの塊

毎フレーム GPU へ送るのは、キャラ1体につき次の float の列だけです（4 の倍数にそろえ、RGBA32F のテクスチャ1枚に全キャラ分を並べて1回で送る）。

| 位置 | 中身 |
|---|---|
| 0〜7 | キャラの置き方（2×3 の行列）。ゲーム側が決める |
| 8〜 | 骨ごとに 8 個：2×3 の行列（骨の今の姿 × 基準の姿の逆） |
| 次 | パーツごとの不透明度 |
| 次 | 差分ごとの重み |
| 次 | 色ごとに 8 個：X と Y（描く色 = 画像の色 × X ＋ アルファ × Y）（0.4〜） |

見本のキャラ（骨 9・パーツ 16・差分 13・色 1）で 120 個＝480 バイトです。

## マスクと合成

マスク（Live2D のクリッピングと反転、Spine のクリッピング）は「**画面と同じ大きさのマスク画像**」で行います（2026-10-30 決定）。

1. 全キャラのマスク用のパーツだけを、1 回のインスタンス描画で、画面と同じ大きさの RGBA8 の画像に描く。マスクごとにチャンネル（最大 16＝画像 4 枚、同時に書き出す）を分け、重なりは MAX で合わせる
2. 本番の 1 回の描画で、マスクで切り抜かれるパーツだけがその画素のチャンネルを読み、不透明度に掛ける（反転なら 1 − 値）

キャラが何体いても描画は 2 回。縁は画像の透明度のままなめらか。マスクの形は描く順に関係なく決まる（Live2D と同じ）。Spine のクリッピングの多角形は、書き出し時に三角形に分けて「描かない・全体を覆う」パーツにする（骨の重みで動くので普通のメッシュと同じく GPU で変形する）。

弱点は、別々のキャラが重なり、さらに切り抜かれるパーツが自分のマスクからはみ出して、相手の同じチャンネルのマスクの上に乗った時に見えてしまうこと。これを避けたい時は `strictMasks`（キャラごとにマスクと本番を描く。キャラ 1 体に 2 回）を使う。

比べた方式（`build/maskbench`、headless Chromium・SwiftShader・900×600、見本に試しのマスク 4 組。1 フレームの GPU 待ちを含む時間）：

| 方式 | 描画回数 | 1 体 | 50 体 | 200 体 |
|---|---|---|---|---|
| マスク無し（基準） | 1 | 8.7 ms | 87 ms | 270 ms |
| **画面サイズのマスク画像（採用）** | **2** | 8.4 ms | 111 ms | 334 ms |
| ステンシル・キャラごと | 1 体あたり 1 + 2 × マスク | 9.3 ms（12 回） | 122 ms（600 回） | 386 ms（2,400 回） |

ソフトウェアの GPU なので時間は塗る量で決まり、本物の GPU の比率とは違う（本物の GPU ではマスクの描画は小さく、ステンシル方式は描画命令の数が重くなる）。2 つの方式の絵は、1 体では最大 1/255 の差、重なった 50 体では全画素の 0.01% だけ違った（キャラをまたいだ漏れ）。ほかに考えた方式：ステンシルを全キャラまとめて区切る（描画は少ないが重なったキャラの前後が崩れる）、多角形をシェーダーで判定（1 回で済むが Spine の多角形しか表せない）、Live2D 式のマスク用アトラス（マスクの範囲を毎フレーム CPU で求める必要がある）。

## ワープ格子

Live2D のワープデフォーマに当たる格子は、**実行時に評価**する（2026-10-30 決定）。CPU は毎フレーム格子の制御点だけを計算してフレームの塊に入れ（5×5 の格子で延長の点を含め 49 点＝392 バイト）、各頂点は GPU が一様な 3 次 B スプラインで曲げる。描画は 1 回のまま。入れ子の格子は CPU が子の制御点を親の曲面で動かすので、Live2D と同じ意味で正確。

比べた方式（見本の顔、5×5 の格子。`build/maskbench`、ソフトウェアの GPU・200 体、基準 237 ms／フレーム）：

| | 書き出し時に差分へ焼く（A） | 実行時に格子（B、採用） |
|---|---|---|
| 振り向き 30 度の中で目を閉じた時のずれ | 最大 11.9 px（目の差分が格子で曲がらない。振り向きと目の組み合わせの角の補正を入れない場合） | 0 |
| データ（格子のキーフォーム 8 つ、頭の頂点 1,553） | +146 KB | +1.8 KB |
| GPU（全頂点に掛けた場合） | +44 ms（+19%） | +76 ms（+32%） |
| フレームの塊 | 増えない | 格子 1 つあたり +392 バイト |

本物の GPU では頂点の計算より塗る量が重いので、GPU の差はこれより小さい見込み。

焼く方式でも、軸の組み合わせごとの角の補正を足せばずれは減る。読み込み・書き出しの担当が `tests/warp` で試算した結果は、範囲ごとのモーフ（モデルにある角の補正を含む）で最大 1.24 px。ただし、入れ子の格子の中の差分は外の格子の 3 次 B スプラインを通るので、重みに対して直線にならず、組み合わせのモーフを足すと逆に悪くなることがある（13 px）。glTF などへ焼く時の扱いは読み込み・書き出しの担当が決める。

## テクスチャの取り方（近い色、2026-11-10、利用者の声 #54）

ピクセルアートのために、テクスチャを「近い色」（nearest：その点の 1 テクセルをそのまま）で取る選択肢がある。形式は変えず、描く時に選ぶ。

- 芯の絵（書き出し）：`ugo_raster_instance_ex(..., flags)` の `UGO_RASTER_NEAREST`（今の `ugo_raster_instance`・`_masked` は今までどおり滑らか）
- Web：`new UgoRenderer(gl, model, images, { sampling: 'nearest' })`、または `renderer.setSampling('nearest' | 'linear')`（アトラスのフィルタを NEAREST にする。ミップマップは使わない）
- エンジン：テクスチャの設定（Unity の Filter Mode = Point、Godot の texture_filter = Nearest、three.js の NearestFilter）で同じになる
- 整数倍に拡大するとドットがそのまま出る。整数倍でない拡大・縮小ではドットの幅がそろわないのは、他のツールと同じ

## 描画順（1.0）

Live2D の描画順のキーに当たる。パーツごとの値（パラメータとアニメで変わる）の小さい順に描き、同じ値は保存の順（2026-11-04 決定、要望 8）。

- 芯：値を求めてから、前のフレームの並びを元に挿入ソートする（ほぼ並んでいるので速い）。動いた量が多い時（パーツ数の 8 倍を超える移動）はマージソートに切り替える。同じ値は保存の順と決めてあるので、答えは並べ方によらず 1 つで、どの環境でも同じ
- 速さ（wasm、300 パーツ、更新 1 回）：描画順の無いモデル 0.7 µs。10 パーツの前後が毎フレーム入れ替わる時 +2.9 µs、全部が毎フレーム逆さになる最悪の時 +17 µs（挿入ソートのままなら +46 µs だった）。並びが変わらない時は +0.7〜1.2 µs
- 描く側：インスタンス描画は全キャラが同じインデックスの並びを使うので、並びがキャラごとに違うとまとめて描けない。そこで、芯が並びの印（保存の順なら 0、他は並びのハッシュ）を出し、Web の描き方は印ごとにインデックスの並びを作って覚える（8 通りまで。超えたら一番前に使った物の場所に作り直す）。描く順は崩さず、隣り合うキャラで同じ並びの物をまとめて描く。描画順を使わないモデルは今までと同じ 1 回
- 比べた方式：深度で並べる（半透明の合成と合わないので採らない）、キャラごとに描く（何体でも 1 回、の良さが消える）

**合成**：通常と加算は同じ合成の式で描ける（加算はアルファを 0 にして出す）。乗算・スクリーンは、`WEBGL_blend_func_extended`（二つの出力で合成する GPU の機能）があれば同じ 1 回の描画で描く（下の色 × 2 つ目の出力 ＋ 1 つ目の出力、で 4 種類とも表せる）。無い時は、合成の式が変わる所で描画を分ける（全キャラまとめて。重なったキャラの前後は崩れうる）。式は [形式](形式.md) の表。

## アニメの重ね（足し算と覆い、2026-11-10、形式は変えない）

毎コマ `ugo_reset_params` で基準に戻し、`ugo_apply_animation` を重ねる。混ぜ方は、トラックのある物だけ p ← p + (v − p)·w（トラックの無い物には触らない。値が基準のトラックは「基準へ戻す」意味を持つ）。

`ugo_apply_animation_ex(in, anim, t, w, flags, mask)` で層の作り方を選べる（Web は `inst.play(name, t, w, { add, mask })`、覆いは `model.animationMask({ bones, parts, params, morphs, constraints, colors })`）：

- `UGO_ANIM_ADD`：基準からの差を足す（p ← p + (v − 基準)·w）。呼吸や待機の上に、手振り・うなずきを足す。基準は、骨の差と差分の重みは 0、パラメータは既定値、不透明度・描画順・制約・色はそれぞれ自分の値
- 覆い：種類ごとに「当てる物」の 1 バイトの列（骨・パーツ・パラメータ・差分・制約・色）。列が無い種類は全部に当てる。上半身だけ手を振る、顔だけ表情のアニメ、など

どちらも無ければ `ugo_apply_animation` と同じ（同じ関数に渡す）。

Web の `UgoAnimator` が層・クロスフェード・順に流す（queue）・速さ・範囲（from・to）・足し算・覆い・止める時のフェード・`end` の知らせをまとめて持つ（Live2D のモーションの管理、Spine の AnimationState に当たる）。毎フレーム `animator.update(dt)` → `inst.reset()` → `animator.apply(inst)` → パラメータ・表情 → `inst.update(dt)`。

## ポーズとドラッグ（エディタ、2026-11-10、形式は変えない）

- `ugo_set_bone_offset(in, bone, pose[7], w)`・`ugo_get_bone_offset`：アニメ無しで骨を動かす（回転・x・y・scale・shear の基準からの差。トラックと同じ値）。Web は `inst.setBoneOffset('arm', { rotate: 30 })`・`inst.boneOffset('arm')`（角度は度）
- `ugo_set_bone_world(in, bone, world[6])`：骨を世界の姿に置く（親の今の姿の下で差を逆算）。親を動かしても子を動かさない「補正」（動かす前の boneWorld を覚え、後で置き直す）や、ワールドの軸での数値入力に。Web は `inst.setBoneWorld('hand', w)`
- `ugo_solve_ik_to(in, bone, count, x, y, iterations)`：骨の先（長さの端、長さが無ければ元）を点へ寄せる。骨と親を count 本まで、前の update の姿から CCD で回し、回転の差に足す。鏡に映した親の下でも合う。Web は `inst.dragBone('hand', x, y, 2)`。エディタはマウスを動かすたびに呼んで update する（制約がある時は数回で落ち着く）

## 当たり判定と範囲（エディタ、2026-11-10、形式は変えない）

`ugo_pick_part(in, deformed, x, y, min_opacity)`：`ugo_deform_cpu` の位置で、点にある一番手前のパーツ（描画順の後ろから、マスクの中だけ・反転は外だけ、描かないパーツと不透明度が min_opacity 以下のパーツは飛ばす）。テクスチャの透明な所も当たりに数える（要るなら呼ぶ側で画素を見る）。`ugo_bounds(in, deformed, part, box)`：パーツの変形後の四角、part = −1 で描かれる全部。Web は `inst.pickPart(x, y)`・`inst.bounds('arm')`・`inst.bounds()`。

## 物理を落ち着かせる・一部だけ変形（2026-11-10、形式は変えない）

- 物理は update の dt に合わせて 120 Hz 以上の刻みで進めるので、低い fps でも同じ揺れ方（補間は要らない）
- `ugo_settle_physics(in, seconds)`：今のパラメータと姿のまま、揺れ物を最大 10 秒ぶん進めて落ち着かせる（場面の切り替えで、新しい姿へ揺れながら入らないように）。Web は `inst.settlePhysics(2)`
- `ugo_set_wind(in, x, y, gust)`：揺れ物の鎖に風（モデル座標の px/秒² の加速度を重力に足す）。gust で強さが時刻の関数（ゆっくりした波の和）で揺らぐので、同じ時刻なら同じ揺れ（巻き戻せる）。モデルは直さない。Web は `inst.setWind(600, 0, 1)`。パラメータの物理（向きを持たない）には効かない。物理ごとの風の強さを形式に持つのは 1.2 の E3
- `ugo_deform_part_cpu(in, part, out)`：1 つのパーツの頂点だけ CPU で変形（エディタの選択表示）。Web は `inst.deformedPart('arm')`
- 重いモデルの速さ（2026-11-10 に測り直し、Spine から持ち込んだ提供データ、1 体あたり）：提供のモデル C 止まった姿勢 8 µs・アニメ中 16 µs、提供のモデル B 8・19 µs、提供のモデル A 10・27 µs（アニメを当てるだけ 5.5 µs）。半分以上は骨の姿の計算で、親が動くと 395 本すべてを計算し直す。結果を同じビットに保ったままの小さな手直し（親が計算し直された子は比べずに計算する）は、アニメ中は 1〜2 µs 速くなるが止まった姿勢が遅くなるので入れていない。次の段は、骨を深さごとにまとめて SIMD で計算する（結果は同じにできる）か、float の精度で計算する（結果が少し変わる）か

## 当たりの領域（2026-11-10、形式は変えない約束）

アプリが「頭を触った」を知るための領域は、描かないパーツ（`maskOnly`）に `hit:頭の名前`・`当たり:名前`（全角の `：` も）と名前を付けて作る。`ugo_pick_area(in, deformed, x, y, only)` は、only で選んだパーツのうち点にある一番手前の物を、描くかどうか・不透明度に関わらず返す。Web は `model.hitAreas`・`inst.hitTest(x, y)` → `'頭の名前'` か null。骨や変形にそのまま付いて動く。正式な表（名前・パーツ）は 1.2 の候補（E6）

## ほかの言語から（2026-11-10、形式は変えない）

## 各環境への出し方

芯は C99 で、メモリの確保・ファイルの読み書き・GPU の操作を一切しません（呼ぶ側がメモリを渡す）。どの環境でも同じ芯を包み、各環境では**頂点シェーダー1本**を書くだけにします。

| 環境 | 状態 | 方法 |
|---|---|---|
| Web（ブラウザ） | ✅ 試作 | 芯を WASM（約 40 KB、clang だけ）、WebGL2 で描く。アトラスの全ページをテクスチャ配列に入れて 1 回で描く。WebGPU も（`web/ugo_webgpu.js`、同じ絵。無ければ WebGL2） |
| GIF・APNG・PNG 連番・スプライトシート | ✅ 試作 | ブラウザ（GPU で描いて読み戻す）と `ugo_export`（CPU で描く） |
| 動画（MP4・WebM の透明つき） | ✅ 試作 | `ugo_export` が ffmpeg へ渡す |
| ネイティブ（C・C++） | ✅ 試作 | 静的・共有ライブラリ（CMake、Windows・macOS・Linux） |
| Unity | 予定 | 共有ライブラリを C# から呼ぶ＋HLSL の頂点シェーダー。フレームの塊はテクスチャか StructuredBuffer で渡す |
| Godot | 予定 | GDExtension で芯を包む＋Godot のシェーダー言語。ArrayMesh に静的データを1回入れる |
| Unreal Engine | 予定 | プラグイン（C++ から芯を呼ぶ）＋マテリアルの頂点の位置ずらし、または独自の頂点ファクトリ |
| スマホ | 予定 | 上の各エンジン経由、またはブラウザ（WebGL2） |

頂点シェーダーでテクスチャを読めない古い環境では、CPU の参照計算（`ugo_deform_cpu`）に切り替えられます。

| キャラ | 骨・制約 | 止まった姿勢 | アニメ中 |

| 提供のモデル A | 395・16 | 53.5 → **16.6 µs** | 69.8 → 35.0 µs |

（2026-10-30、左が前、右が後。上の表とは別の機械）速くした所：骨の姿（世界の行列）を必要になった時にだけ計算する（制約が骨を動かしても子孫をすぐには計算し直さず、最後に 1 回）、mix が全部 0 の transform 制約を飛ばす、骨ごとに前の角度の sin・cos を覚える、割り算を掛け算に（sin・cos・atan の係数、平方根は逆数の平方根のニュートン法）、アニメの値が変わらないトラックはキー 1 個に、トラックを種類ごとに並べる。前と後の骨の姿は 3 体・全アニメで一致（行列は同じビット、位置の差は最大 0.000015 px）。アニメ中の残りの半分はトラックを読む時間（提供のモデル A は 1 つのアニメに骨のトラックが 2,723 本、その 85% は値が変わらない）。

2026-10-31 の 2 回目（同じ機械で前と後を続けて測る。1 体あたり、8 体を回して 3 回の最小）：

| キャラ | 止まった姿勢 | アニメ中 | アニメを当てるだけ |
|---|---|---|---|
| 提供のモデル C | 10.3 → **8.8 µs** | 19.7 → 17.4 µs | 7.1 → 3.6 µs |
| 提供のモデル B | 11.0 → **8.7 µs** | 24.1 → 21.1 µs | 10.0 → 5.7 µs |
| 提供のモデル A | 16.8 → **10.8 µs** | 35.9 → 31.3 µs | 14.5 → 7.2 µs |

- 骨の姿は「親の姿」と「自分の局所の値」だけで決まるので、どちらも前に計算した時と同じビットなら計算しない（骨ごとに 14 語を覚える。インスタンスのメモリが骨 1 本あたり 56 B 増える）。止まった姿勢では、制約が毎フレーム同じ値を書き直しても、子孫の計算は起きない
- 姿が変わらなかった骨は、スキンの行列も前のまま（書き直さない）
- キーの探し方を、枝分かれの無い二分探索に（予測の外れが無い）。探す区間は前と同じなので、値も同じ
- トラックを種類ごとのまとまりで回す（種類・置き場所・キー 1 個かを、トラックごとに調べない）
- 前と後のフレームの塊は、3 体の全アニメ（36 個など）、見本、テストのデータで同じビット（アニメを重ねる・パラメータを動かす・置き方を変える場合も含む）
- ワープ格子の中の骨があるモデルは、姿を格子が後から書き直すので、この使い回しをしない
- 目標の 10 µs は止まった姿勢ではほぼ届いた。アニメ中は届いていない：提供のモデル A の最初のアニメは根元の骨が動くので、395 本すべての姿を毎フレーム計算し直す（1 本あたり約 60 ns）。ここを縮めるには、計算を float の精度にする（結果が少し変わる）か、SIMD でまとめて計算する必要がある

2026-11-13（形式は変えない。命令数で比べる：この機械は同じプログラムの時間が ±25% ぶれる。8 体・最初のアニメ、1 ステップ、valgrind）：値の変わらないトラックを、読み込む時に（書く場所、値）の表にまとめて 1 回で当てる（表はモデルのメモリ、`ugo_model_mem_size_for` に入る。少なく渡すと 1 本ずつ当てる。結果は同じビット）。

| キャラ | アニメを当てるだけ | アニメ中 | 止まった姿勢 |

| 提供のモデル B | 79k → **62k** | 267k → 245k | 118k → 120k |

アニメ中の残りは、骨 1 本あたり約 600 命令の姿の計算（double の sin・cos、受け継ぎ方、スキンの行列）。結果のビットを変えずに縮めるには、同じ深さの骨を SIMD でまとめて計算する（wasm は `-msimd128` が要る）のが次の手。

大きなモデル（2026-11-10、`tests/big_bench.mjs` の合成のキャラ。160 パーツ・27,564 頂点・差分の項目 62,094、400 パーツ・68,790 頂点。Linux、1 スレッド、-O2）：1 フレームの芯の計算は 5〜8 µs（WASM は 9〜12 µs。頂点は GPU が動かす）、読み込みの確かめ 0.3〜0.8 ms、CPU の変形（`ugo_deform_cpu`）0.4〜1.1 ms、1 体ぶんのメモリ 15〜18 KB（モデルはファイルのバイトをそのまま使う）。重いのは CPU で描く所（`ugo_export`）で、512×512 で 45 → **33 ms**（160 パーツ）、94〜110 → **76〜87 ms**（400 パーツ）に縮めた：三角形の辺の値を三角形ごと・行ごとに 1 回だけ計算し、行の中で塗る所を過ぎたら止める（辺の値は行に沿って一方向にしか動かないので、塗る所は 1 続き）。描いた絵は 6 つのモデルで前と同じビット（なめらか・最近傍とも）。残りはテクスチャの取り方（双一次）で、ここを変えると絵が少し変わるので、今は触らない

ブラウザ（headless Chromium、ソフトウェアの GPU、205 体）：Ugo9 は描画 1 回・転送 90 KB／フレーム。CPU で変形する比較の方式は描画 205 回・転送 3.3 MB／フレーム。両方式の絵の差は最大 8/255 ほど（同じ絵）。

本物の GPU では、GPU 側の時間（塗る面積・重なり）が次の壁になります。透明な所を削ったメッシュ（見本は透明なマス目を自動で省く）と、不透明な内側と半透明の縁を分ける工夫で減らします。

### エディタの作り直し（大きなキャラ）

エディタは編集のたびに、作業用 JSON をコンパイルし、モデルを読み、描画の部品を作り直します（`editor/live.js`）。大きなキャラで測るため、PSD から作ったキャラほどの大きさの作業用 JSON を合成しました（`tests/big_bench.mjs`。提供データは使っていない）。

- 中身：パーツ 160（格子のメッシュ）、頂点 27,564、パラメータ 30、ワープ 11（顔の中に 9 個の入れ子）、デフォーマ 64（1 つで 6 パーツを全頂点の差分で動かす）、作業用 JSON 2.2 MB、.ug9 2.7 MB
- パーツの 1/4 はワープ格子の顔、1/4 は体の格子、1/4 は骨、1/4 は髪の骨 2 本の重み

headless Chromium（ソフトウェアの GPU）、アトラス 4096 px（`setModel` で使い回す）、1 回の作り直しの中央値です（ms）。

| | コンパイル | 読み込み | setModel | インスタンス | 合計（描画を除く） |
|---|---|---|---|---|---|
| 前 | 95 | 0.9 | 11 | 0.1 | 107 |
| 後 | **20** | 0.7 | **3.5** | 0.1 | **24** |

コンパイルの区分（後、ms）：パーツ 8、デフォーマ 6、重みと差分の表 3、書き出し 3、その他 1 未満。

- パーツ 80（頂点 1.4 万）なら合計 18 ms で、1 フレームに収まります。160 は 1.5 フレーム、320（頂点 5.5 万）は約 4 フレームです。エディタは引きずる間の編集をまとめて作り直すので（`live.js` の flush）、160 パーツでも頂点を引きずる間に 30〜40 回／秒は描き直せます
- パラメータのスライダーは作り直しをしません（`set_param` だけ）
- 描画（25 ms）はソフトウェアの GPU で塗る時間です。本物の GPU では 1〜2 ms 程度なので、表から外しました
- 速くした所（形式も出力も同じ。前と後の .ug9 は、見本・テストのデータ・合成のキャラ・のり付きで同じバイト。壊した入力 15,000 通りでもエラーの文が同じ）：
  - どの差分も無い頂点（ほとんど）の Map を作らない
  - 差分を頂点ごとの平らな配列に入れる（差分は番号順に入るので、並べ替えは不要）
  - 骨 1 本のパーツは影響の表を 1 つ共有する
  - 位置・UV・三角形・骨の番号と重み・差分を、先に大きさを数えた型付き配列に入れる
  - 書き出しは配列ごとに型付きの窓でまとめて書く（リトルエンディアンの時。それ以外は前と同じ 1 個ずつ）
  - 頂点ごとに作っていた文字列（エラーの場所）を、パーツごとに 1 回にする
  - `setModel` の index の組み立てで、配列の展開（`push(...part)`）をやめる
- 1 フレームに入らない大きさで、さらに速くするなら：編集したパーツだけを作り直す差分コンパイル（エディタから「どこを変えたか」を受け取る必要がある）か、Worker でのコンパイル
- 区分ごとの時間は `compileUgo(json, { timings: {} })` で取れます

### アトラスを GPU に上げる（開く時）

`tests/atlas_bench.mjs`：4096 px の 4 ページ（最後のページは半分の大きさ）を、headless Chromium（ソフトウェアの GPU）で上げる時間。

- PNG を読む（`loadImage`）：約 240 ms
- `setImages`：約 740 → **450 ms**。小さいページの余白を透明にするために、全ページ分の 0 の配列（4 ページで 256 MB）を作って上げていた。WebGL のテクスチャは最初から 0 なので、やめた。描かれる絵は同じ（小さいページを含むモデルで、前と後のピクセルが一致。web・mask・editor・editor_flow・compare_frames のテストも通る）
- 残りはピクセルの写し（約 260 ms）とミップマップで、どちらも本物の GPU では速いはず。11/4 に PC で測る：`renderer.timings` に、最後の `setModel`・`setImages` の CPU の時間（ms）が入る

## 安全

`.ug9` は他人から受け取る前提です。読み込み時に、全ての数・番号・範囲・浮動小数点の値（NaN・無限大）を検査し、不正なら読み込みを断ります。テストでは、ファイルを 3,000 通りに壊して（ビットの反転・切り詰め・でたらめな値）、AddressSanitizer と UBSan の下で落ちないことを確かめています。
